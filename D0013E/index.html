D0013E.

Programming a computer from the bottom up. I wrote a recursive string decoder in MIPS assembly, made it run on a pipelined CPU, exposed it to interrupts, built a tiny kernel that switches between three programs on a timer, and finally wrote the same decoder again in C and in Rust to compare what the compilers make of it.

Course labs

L1b
Decrypting a string
A recursive decode and a pseudo-random codgen in MIPS assembly. Every local of decode lives on the stack at a fixed offset from the frame pointer, and codgen counts zero bits with the x &= x - 1 trick, since MIPS here has no multiply or divide.
L2
Pipelined MIPS and interrupts
Made the decoder run on a 5-stage pipeline: filled delay slots, added bubbles after loads, and replaced pseudo-instructions with real ones. Measured the speed-up (3.470 instead of 4) and explained why, then ran it with timer and keyboard interrupts firing.
L3a
User code and a kernel
A user program that can't touch the hardware asks the kernel to print through SYSCALL. Wrote the exception handler in kernel space: read the cause from CP0, check the service code, write to the I/O port, return with RFE.
L3b
Multitasking
Three programs share one CPU. On each timer interrupt the kernel saves 27 registers on the running program's stack, stores its PC, $gp and $sp in a process control block, and resumes the next one, round robin.
L4
From C to assembly
The same decoder in C, run on Linux first and then cross-compiled for MIPS at optimization levels 0 to 3, to compare the compiler's calling convention and stack use with my hand-written assembly.
L4r
Rust edition
The decoder once more in Rust: a hosted version that checks itself on the "abc" string first, and a no_std bare-metal build for a big-endian MIPS target with its own panic handler and linker script.

    Why it's not 4: a value loaded from the stack can't be used in the very next cycle

    Every local on the stack
    The assignment requires x, y, m and r to live on the stack, not in registers. Every time one is reloaded, the next instruction has to wait a cycle. Those bubbles are why the speed-up lands under 4.
    What interrupts cost
    The timer fires about every 1024 cycles, so roughly 27 times in a run. They added 315 cycles in total, about ten instructions each for the handler. One key press added another 14.

      What I learned

      The stack is just memory with rules.

      Drawing the stack frame for every function before writing it, with the frame pointer as a fixed anchor, is what made a recursive function in assembly manageable.

      Pipelines don't come for free.

      Delay slots and load-use bubbles meant my code needed small, careful changes to run at all on the pipelined CPU, and the speed-up depends on how the code is written, not just on the hardware.

      A context switch has to be invisible.

      For a program not to notice it was paused, the kernel must save every register it could have touched and put each one back exactly. Missing a single register breaks a program that did nothing wrong.

      Same algorithm, three languages.

      Writing the decoder in assembly, C and Rust showed what a compiler does for me. In Rust I had to use wrapping arithmetic on purpose, because plain addition panics on overflow in a debug build.
